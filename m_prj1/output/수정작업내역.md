**원인**: Windows PowerShell에서 `-D` 파라미터가 분리되어 `local`이 Maven 라이프사이클 phase로 해석됨

**해결**:

```

**증상**: `onStatus` 핸들러가 4xx를 중복 처리, 5xx 처리 누락

### 오류 3: 환경 변수 미설정으로 인한 기동 실패

**증상**: `APPLICATION FAILED TO START` — `DATABASE_URL`, `JWT_SECRET`, `S3_ACCESS_KEY` 등 필수 환경 변수 없음

**원인**: `application.yml`의 `${DATABASE_URL}`, `${JWT_SECRET}`, `${S3_ACCESS_KEY}`, `${S3_SECRET_KEY}`는 기본값 없음. `spring-boot:run`은 `.env` 파일을 자동으로 읽지 않음.

**해결**: `application-local.yml` 재구성 (Docker Compose 기준 설정값 포함)

| 설정 | 값 |
|------|-----|
| DB URL | `jdbc:postgresql://localhost:5432/appdb` |
| DB User | `postgres` (docker-compose 기준) |
| DB Password | `postgres` |
| JWT Secret | `local-dev-secret-key-min-32-characters-long` |
| S3 Endpoint | `http://localhost:9000` (MinIO) |
| S3 Access Key | `minioadmin` |

> **발견된 부가 오류**: 초기 `application-local.yml`에 `appuser/apppass` 설정 → docker-compose의 `postgres/postgres`와 불일치 → DB 연결 실패. 수정 완료.

```
→ **실패**: Windows `mvnw.cmd`에서 `.mvn/jvm.config`가 읽히지 않음. 로그에 `No active profile set` 메시지 지속 확인

### 오류 5 재수정: `pom.xml` 플러그인 설정으로 변경 (성공)

**근본 원인**: `.mvn/jvm.config`는 Maven JVM 자체의 인수로 설정되나, Windows `mvnw.cmd` 환경에서 `spring-boot:run`이 실행하는 Spring Boot 애플리케이션에 `spring.profiles.active`가 전달되지 않음

**최종 해결**: `pom.xml` Spring Boot Maven 플러그인에 `<profiles>` 직접 설정

```xml
<!-- pom.xml -->
<plugin>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-maven-plugin</artifactId>
    <configuration>
        <profiles>
            <profile>local</profile>
        </profiles>
        ...
    </configuration>
</plugin>
```

**수정 파일**:
- `pom.xml` — `<profiles><profile>local</profile></profiles>` 추가
- `.mvn/jvm.config` — 내용 제거 (충돌 방지)

> **운영 배포 시 주의**: `pom.xml`의 `<profiles>` 블록을 제거하고 실제 환경 변수(`SPRING_PROFILES_ACTIVE`)를 사용해야 합니다.

### 문제 6 (Critical): `TIMESTAMPTZ` vs `LocalDateTime` 스키마 검증 실패

**증상 (예상)**:
```
Schema-validation: wrong column type encountered in column [created_at] in table [users];
  found [timestamptz (Types#TIMESTAMPTZ)], but expecting [timestamp (Types#TIMESTAMP)]
```

**원인**: Hibernate 6 + `ddl-auto: validate` 환경에서 PostgreSQL `TIMESTAMPTZ`(타임존 포함)는 Java `OffsetDateTime`/`Instant`에 매핑. JPA 엔티티가 `LocalDateTime`(타임존 없음)을 사용하므로 타입 불일치

**영향 파일**:
- `V1__init_schema.sql` — `users`, `resources`, `notification_histories` 테이블
- `V2__add_file_metadata.sql` — `file_metadata` 테이블

**수정**: 모든 `TIMESTAMPTZ` → `TIMESTAMP` 변경

```sql
-- 수정 전
created_at  TIMESTAMPTZ  NOT NULL DEFAULT NOW()

-- 수정 후
created_at  TIMESTAMP    NOT NULL DEFAULT NOW()
```

---

### 문제 7 (High): `UpdateResourceRequest.status` 업데이트 미반영

**증상**: `PUT /api/v1/resources/{id}` 요청 시 `status` 필드를 전달해도 DB에 반영 안 됨

**원인**: `Resource.update()` 메서드가 `name`, `description`만 처리

```java
// 수정 전 — status 무시
public void update(String name, String description) {
    this.name = name;
    this.description = description;
}

// 수정 후 — status 반영
public void update(String name, String description, Status status) {
    this.name = name;
    this.description = description;
    if (status != null) this.status = status;
}
```

**수정 파일**:
- `domain/resource/entity/Resource.java` — `update()` 시그니처 변경
- `domain/resource/service/ResourceService.java` — `status` 파싱 후 `update()` 전달

## 5차 작업 — Flyway 체크섬 불일치 오류 수정

### 오류 10 (Critical): Flyway Migration Checksum Mismatch

**증상**:
```
Validate failed: Migrations have failed validation
Migration checksum mismatch for migration version 1
-> Applied to database : 946213054
-> Resolved locally    : 1346166465
Migration checksum mismatch for migration version 2
-> Applied to database : -355733159
-> Resolved locally    : -2137020575
```

**원인**: 이전 작업(오류 6)에서 `V1__init_schema.sql`, `V2__add_file_metadata.sql`의 `TIMESTAMPTZ → TIMESTAMP` 수정을 진행했으나, 해당 마이그레이션이 이미 DB에 적용된 상태였음. Flyway는 이미 실행한 마이그레이션 파일의 변경을 허용하지 않으며, 체크섬 검증 실패로 앱 기동 거부.

**해결**:

1. `application-local.yml`에 `clean-on-validation-error: true` 추가 (로컬 전용)
   - 체크섬 불일치 발생 시 Flyway가 DB 스키마를 자동 정리 후 마이그레이션 재적용

```yaml
spring:
  flyway:
    clean-on-validation-error: true  # 로컬 전용: 체크섬 불일치 시 자동 clean 후 재적용
```

2. DB 볼륨 1회 리셋 필요 (현재 잘못된 이력 제거):
```powershell
docker compose down -v
docker compose up -d
.\mvnw.cmd spring-boot:run
```

**수정 파일**: `application-local.yml`

> **주의**: `clean-on-validation-error: true`는 로컬(`application-local.yml`)에만 설정. 운영 환경에서는 절대 사용 금지 (전체 DB 데이터 삭제됨).

## 6차 작업 — Kakao OAuth2 redirect-uri 미설정 오류 수정

### 오류 11 (Critical): `redirectUri cannot be empty`

**증상**:
```
Caused by: java.lang.IllegalArgumentException: redirectUri cannot be empty
  at ClientRegistration$Builder.validateAuthorizationCodeGrantType
  → clientRegistrationRepository Bean 생성 실패
  → OAuth2AuthorizedClientManager 생성 실패
  → SendGridClient FactoryBean threw exception
  → sendGridEmailAdapter Bean 생성 실패
```

**원인**:
- `application.yml`의 Kakao OAuth2 registration에 `redirect-uri` 누락
- Google은 Spring Security 내장 Provider → `redirect-uri` 기본값 자동 제공
- Kakao는 커스텀 Provider → `redirect-uri` **반드시 명시** 필요

**왜 SendGridClient도 함께 실패했나?**
Feign은 각 클라이언트마다 독립적인 자식(child) ApplicationContext를 생성. 그 자식 컨텍스트 안에서도 Spring Security OAuth2 자동설정이 동작하며, 동일한 `redirect-uri` 오류가 발생해 `SendGridClient` Bean 생성 자체가 불가능했음.

**해결**: `application.yml` Kakao registration에 `redirect-uri` 추가

```yaml
# 수정 전
kakao:
  client-id: ${KAKAO_CLIENT_ID}
  client-secret: ${KAKAO_CLIENT_SECRET}
  client-authentication-method: client_secret_post
  authorization-grant-type: authorization_code
  scope: profile_nickname, account_email

# 수정 후
kakao:
  client-id: ${KAKAO_CLIENT_ID}
  client-secret: ${KAKAO_CLIENT_SECRET}
  client-authentication-method: client_secret_post
  authorization-grant-type: authorization_code
  redirect-uri: "{baseUrl}/login/oauth2/code/{registrationId}"
  scope: profile_nickname, account_email
```

## 7차 작업 — 프론트엔드 tsconfig 오류 수정

### 오류 12 (High): `@tsconfig/node20` 패키지 미설치

**증상**:
```
[vite] Pre-transform error: failed to resolve "extends":"@tsconfig/node20/tsconfig.json"
  in D:/Marchall_CLAUDE/m_prj1/output/project/frontend/tsconfig.node.json
```

**원인**: `tsconfig.node.json`이 `@tsconfig/node20` 외부 패키지를 `extends`로 상속하는데, 해당 패키지가 `node_modules`에 설치되지 않음

**해결**: `tsconfig.node.json`에서 외부 패키지 의존 제거, Node20 핵심 설정을 인라인으로 직접 작성

```json
// 수정 전
{
  "extends": "@tsconfig/node20/tsconfig.json",
  ...
}

// 수정 후 — 외부 패키지 없이 동일 설정 인라인 포함
{
  "compilerOptions": {
    "target": "ES2022",
    "lib": ["ES2023"],
    "module": "ESNext",
    "moduleResolution": "bundler",
    "strict": true,
    "esModuleInterop": true,
    "skipLibCheck": true,
    ...
  }
}
```

**수정 파일**: `frontend/tsconfig.node.json`
