# 배포 전략 플랜

> 대상: **Vue 3 (Vite) + Spring Boot 3.3 + PostgreSQL 16 + Redis 7 + MinIO**  
> 현재 코드 기준 아티팩트: 루트 `docker-compose.yml`, `backend/Dockerfile`, `frontend/Dockerfile`  
> 상세 서버 작업 절차는 [aws배포절차.md](./aws배포절차.md)에 정리되어 있으며, 본 문서는 **전략·단계·의사결정**을 담습니다.

---

## 1. 목표와 원칙

| 목표              | 설명                                                                                               |
| ----------------- | -------------------------------------------------------------------------------------------------- |
| 재현 가능한 배포  | 동일 Compose 스택으로 로컬·스테이징·프로덕션 환경 변수만 분리                                      |
| 최소 노출 면      | DB·Redis·MinIO는 호스트에 포트 공개 없이 Docker 내부 네트워크만 사용 (EC2 보안 그룹은 80/443/SSH)  |
| 마이그레이션 안전 | Flyway는 기동 시 또는 전용 잡으로 적용, 백업 후 실행                                               |
| OAuth2 일관성     | `ALLOWED_ORIGINS`, `OAUTH2_REDIRECT_URI`, 콘솔 등록 URI를 환경별로 고정하고 배포 체크리스트에 포함 |

---

## 2. 배포 토폴로지 (단계별)

### Phase A — 단일 EC2 + Docker Compose (현재 권장 기준)

- 한 인스턴스에서 `postgres`, `redis`, `minio`, `backend`, `frontend` 전부 기동.
- 프론트는 Nginx(컨테이너) 80 → 사용자 트래픽, API는 동일 호스트 경로 또는 리버스 프록시로 백엔드와 연동.
- **장점**: 비용·운영 단순, [aws배포절차.md](./aws배포절차.md)와 1:1 대응.
- **한계**: 단일 장애점, 수직 스케일만 가능, DB·스토리지 백업을 직접 설계해야 함.

### Phase B — 관리형 서비스 분리 (트래픽·데이터 증가 시)

| 구성 요소        | 권장 이동                              | 비고                                                      |
| ---------------- | -------------------------------------- | --------------------------------------------------------- |
| PostgreSQL       | Amazon RDS (또는 Aurora)               | 스냅샷·다중 AZ, Compose에서는 `DATABASE_URL`만 변경       |
| 객체 스토리지    | Amazon S3                              | MinIO 제거 또는 개발 전용으로 축소, 앱은 S3 API 호환 설정 |
| Redis            | ElastiCache                            | 세션·캐시; 연결 정보를 환경 변수로 전환                   |
| 프론트 정적 자산 | S3 + CloudFront 또는 Vercel/Netlify 등 | 빌드 시 `VITE_*` 확정, API는 별도 도메인                  |

### Phase C — 고가용·무중단 (필요 시)

- 백엔드 다중 인스턴스 + ALB, 세션/캐시는 Redis 공유, DB는 RDS 다중 AZ.
- 배포: 롤링 업데이트 또는 블루/그린(두 타깃 그룹 또는 태스크 정의 버전).

## 3. 환경 정의

| 환경           | 용도                 | 트리거                       | 데이터                                      |
| -------------- | -------------------- | ---------------------------- | ------------------------------------------- |
| **local**      | 개발자 PC            | 수동                         | 로컬 DB/MinIO 또는 `docker-compose.dev.yml` |
| **staging**    | 통합·QA·OAuth 테스트 | `develop` 머지 또는 수동     | 프로덕션 복제본 아님(마스킹 권장)           |
| **production** | 실서비스             | `main` 태그 또는 승인된 배포 | 백업·모니터링 필수                          |

각 환경에서 **동일 이미지**를 쓰고, 차이는 **환경 변수·시크릿·도메인**만 두는 것을 원칙으로 합니다.

## 4. CI/CD 로드맵

현재 저장소에 워크플로가 없더라도, 아래 순서로 도입하는 것을 권장합니다.

1. **CI (필수)**
   - 백엔드: `./mvnw test` (또는 `verify`), 필요 시 Testcontainers.
   - 프론트: `npm ci`, `npm run build`, `lint`/`type-check`가 있으면 포함.

2. **아티팩트**
   - 옵션 A: 서버에서 `git pull` 후 `docker compose build --no-cache && up -d` (단순).
   - 옵션 B: GHCR/ECR에 이미지 푸시 후 서버는 `pull`만 수행 (버전 고정·롤백 용이).

3. **CD**
   - Staging: `develop` 머지 시 자동.
   - Production: `main` 태그 또는 GitHub Environments 승인 후 SSH/SSM 또는 Runner에서 Compose 재기동.

4. **배포 후 검증**
   - Actuator health, 프론트 루트 200, 대표 API 스모크, OAuth 로그인 1회.

## 5. 설정·비밀 관리

- **로컬**: `.env`는 저장소에 넣지 않고 `.env.example`만 유지.
- **서버**: `/home/ubuntu/app/.env` 또는 Docker secrets; `JWT_SECRET`, OAuth 클라이언트, SendGrid/NCP 키는 절대 이미지에 bake-in 하지 않음.
- **프론트 빌드 타임**: `VITE_*`는 빌드 시 주입. 프로덕션 API 베이스 URL·OAuth 경로가 스테이징과 다르면 **빌드 파이프라인별로 다른 arg** 필요.

---

## 6. 데이터베이스·스토리지

- **Flyway**: 배포 순서는 “백업 → 마이그레이션 → 애플리케이션 재기동”을 문서화하고 스크립트화.
- **백업**: Phase A에서는 `pg_dump` 일정(cron) + 볼륨 스냅샷; Phase B에서는 RDS 자동 백업.
- **MinIO**: 프로덕션 장기 운영 시 S3 이전을 염두에 두고 버킷명·리전·엔드포인트를 설정으로만 바꿀 수 있게 유지.

---

## 7. HTTPS·도메인·OAuth

- Let’s Encrypt 등으로 443 종료 후, [aws배포절차.md](./aws배포절차.md)의 OAuth 리다이렉트 URI·콘솔 설정을 **프로덕션 도메인**에 맞게 갱신.
- `ALLOWED_ORIGINS`에 실제 프론트 오리진만 나열.

## 9. 롤백

- **이미지 태그 배포**: 이전 태그로 `docker compose` 이미지 지정 후 재기동.
- **DB**: 문제 마이그레이션 시 복구 절차(스냅샷 복원 vs 수동 다운)를 사전에 한 페이지로 정리.
- **프론트**: 정적 호스팅이면 이전 빌드 아티팩트로 즉시 스왑.

## 11. 실행 우선순위 (요약 체크리스트)

1. Staging EC2(또는 동일 스택)에 Compose로 전 구동 검증.
2. `.env`·OAuth·CORS·리다이렉트 URI를 스테이징 도메인으로 맞춤.
3. CI에서 테스트 + (가능하면) 이미지 빌드.
4. 프로덕션 Elastic IP·HTTPS·백업 cron 적용 후 첫 배포.
5. 트래픽·데이터 증가 시 Phase B(RDS/S3/ElastiCache) 검토.
